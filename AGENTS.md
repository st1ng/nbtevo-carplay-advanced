## Rules

- **no BMW firmware files** (binaries, libraries, layouts, `carplay.ini` copies, dumps). The build needs none: it links
  against soname stand-ins (`build.sh`). Mapbox's Swift source is not kept here either (downloaded when generating).
- Never commit data from the car: `BACKUP/` (gitignored), logs, `sloginfo` (it contains the CarPlay Wi-Fi SSID/passphrase and
  Bluetooth addresses), phone names, VINs, street names of real routes.
- Comments and messages in English. Keep the minimum of files; no copies of long docs.
- `plugin/` is prebuilt and committed: a source change that changes behaviour is rebuilt and committed together with `plugin/`.
- Code that runs inside a factory process (HmiMain3D, Connectivity, mm-ipod) must never crash or block it: check every word before
  patching, fail closed (log and do nothing), keep network and MOST work on threads of our own, and put no static constructors in
  libraries preloaded into mm-ipod or Connectivity.
- In the car: ask before anything beyond what was asked (system partition, coding, other packages). Never stop `CONN_MOCCA`.
- License: PolyForm Noncommercial 1.0.0 (`LICENSE`, `NOTICE`), the installer included; `src/hudglyphs.h` keeps Mapbox's ISC
  notice (generated by our `tools/hud_glyphs.py` from Mapbox's ISC `ManeuversStyleKit.swift` and `LanesStyleKit.swift`, downloaded, not kept here);
  `src/kombitemplate.h` (unchanged) and `src/kombi.h` (port) carry NBT-AAD's Required Notice.

## Build and verify

```bash
./build.sh                                   # clang + ld.lld (LLD= to override) -> plugin/*.so, texts zip
python3 -m unittest discover -s tests        # about 3 minutes; installer tests run under sh and ksh
```

- Target: ARMv7, QNX 6.5 (`-target armv7-none-eabi -march=armv7-a -mfloat-abi=soft -ffreestanding -fPIC -Os -mno-unaligned-access`),
  C++ without exceptions or RTTI, `-nostdlib`. No libstdc++: no STL, no `new`, no static constructors (zero-initialised PODs only).
- Linking: `ld.lld -shared ... --allow-shlib-undefined` against stand-ins made in `out/stubs` that carry only the sonames
  (`libc.so.3`, `libAppFramework.A.so`, `libCoreFramework.A.so`; the `bmw::` symbols `cpm.cpp` imports become empty functions).
  The outputs are byte-identical to a link against the real libraries. The librghook variants link with
  `--allow-multiple-definition` (each C++ part keeps hidden copies of the EABI helpers).
- QNX's `libc.so.3` lacks `__aeabi_memcpy*` / `__aeabi_memclr*` (each C++ file defines hidden local ones) and has no soft-float
  helpers (no floating point anywhere: `kombi.h` builds IEEE doubles by hand). It has no `__aeabi_uidivmod` either (a `%` by a variable
  made the HMI refuse the plugin, car 2026-11-13: `hudshapes.h` uses `wrapN`) and divides with `udiv` (shift-subtract). After a build,
  `objdump -T plugin/libCarPlayMenu.so plugin/libcppinch.so | grep UND | grep aeabi` must print nothing. Before shipping a new import, check it against the car's `libc.so.3` dynamic symbols: the
  stand-in cannot catch a missing one. Socket calls are in `libsocket.so.3` (not libc); `kombi.h` looks them up with `dlsym`.
- A change that should not change behaviour (comments, formatting, renames of local names): build before and after and compare
  stripped files:
  ```bash
  OC=~/.rustup/toolchains/stable-aarch64-apple-darwin/lib/rustlib/aarch64-apple-darwin/bin/rust-objcopy   # or llvm-objcopy
  $OC --strip-all before.so a; $OC --strip-all plugin/libCarPlayMenu.so b; cmp a b
  ```
  Functions with external linkage (e.g. `namespace hud`) are in the dynamic symbol table, so renaming them changes the stripped
  file. Removing a reference alias (e.g. `Gesture &gesture = g_gesture;`) can change code generation.
- Formatting: `clang-format -i --style=file <file>` (`.clang-format`; on macOS `xcrun clang-format`). Byte tables with per-row
  comments stay inside `// clang-format off` / `on`. Never format `hudglyphs.h` or `kombitemplate.h`.

## The head unit

- NBT Evo: two QNX 6.5 nodes. sshd runs on **hu-jacinto**; the HMI (`HmiMain3D`), Connectivity, mm-ipod and the plugin live on
  **hu-omap** (`on -f hu-omap <cmd>`, or `/net/hu-omap/...`). Root SSH over ENET at `169.254.199.99`; OpenSSH 5.2 offers only an
  `ssh-rsa` host key. `SSH_PASSWORD` in the installer is the root password (committed on purpose, by the owner's decision); ssh gets it
  through an askpass helper (`SSH_ASKPASS_REQUIRE=force`, OpenSSH 8.4+).
- Missing tools: no `head`, `awk`, `tar`, `printf` on hu-omap (possibly no `od`, `cmp`); no `ln`, `sed`, `date` on hu-jacinto; QNX
  `grep` has no `\|` and no `-A`; `scp` may be missing; some images have no `/tmp` (ksh here-documents then need `TMPDIR`).
- `/var` (-> `/fs/sda1`), `/opt`, `/bin` (-> `/fs/sda0/...`), `/opt/hmi/data` and the HMI's `rw` (-> `ID5`) are **path-manager links
  the launcher makes after `/bin/start_screen.sh` runs**: at boot use `/fs/sda1/...`. Path-manager links (`ln -sP`, `pathmgr_symlink`)
  shadow a file in place and are forgotten at every reboot.
- Processes: Connectivity is the CarPlay service (`libconn_carplay.so`, `libconn_carplaydevctrl.so`); it starts **mm-ipod** (the iAP2
  stack) for every CarPlay session. `CONN_MOCCA` is Connectivity's launcher package: stopping it leaves its watchdog registration, and
  the unit resets about a minute later (`/var/dump/wd_err_omap_<pid>.log`, "WD ERROR ... Connectivity ... CODE 1"). Never stop it.
- Rebooting: `starterPackageCtrl -d0 -s/-e HMI` only flips the package state (HmiMain3D keeps running); holding the volume knob does
  nothing on the MINI; `OnOffDSICommander` is missing on HMI 1703; `/opt/sys/bin/sysshutdown` only unmounts. What works is
  `sysmgr_reboot()` on hu-omap (`libcpreboot.so`). The SSH session to hu-jacinto may close a little later.
- CarPlay's `carplay.ini`: the template `/opt/conn/data/carplay/carplay.ini` and **Connectivity's working copy
  `/var/opt/conn/carplay/carplay.ini`**, which is what CarPlay reads. Connectivity rewrites the working copy from the template only
  when coded values change. `[KnobInput]` / `[TouchPadInput]` / `[TouchScreen]` are read once when Connectivity starts, `[Screen]` per
  connection.
- With Connectivity started from our wrapper, CarPlay's own `[CarPlay]` lines no longer reach `sloginfo`; for a trace, rename
  `carplaymenu/Connectivity` for one boot.

## How it fits together

```
HmiMain3D (HMI)                         Connectivity                         mm-ipod (per CarPlay session)
  libCarPlayMenu.so (plugin)              libcppinch.so (LD_PRELOAD)           librghook.so (LD_PRELOAD; one of 4 builds)
    menu, option files                      knob X/Y via setKnobEvt              iAP2 identification + route guidance
    HMI patches (tilts, fullscreen)         2-finger touchpad HID                -> /var/iap/pps/routeguidance
    touchpad + controller hooks  --files->  hidden touchscreen (zoom)            [-kombi] -> KOMBI SOME/IP 0xB006
    hud.h: MOST HUDTerminal <- reads routeguidance                               [-most]  -> MOST HUDTerminal (hud.h)
boot.sh (from /bin/start_screen.sh): path-manager links for the layout, carplay.ini copies, Connectivity and mm-ipod wrappers
```

- The switches are files in `/var/opt/hmi/data/rw/carplaymenu` (`kCfgDir`), one per option; present = on.
- `debug_log` (no menu row; also read from `/fs/sda1/opt/hmi/data/ID5/carplaymenu`, once per library start): the per-event log lines
  (touchpad / knob / zoom events, every HUDTerminal message, every maneuver, rghook's per-message RG lines, KOMBI maneuvers). Without
  it the logs keep start-up and configuration, errors and refusals (the cluster's op f / op 9), and rare state changes.
- Processes get our libraries through **wrappers**: the system binary (`/opt/conn/bin/Connectivity`, `/opt/conn/bin/carplay/mm-ipod`)
  is shadowed with `ln -sP` by a ksh script that puts our library first in `LD_PRELOAD` and execs a copy of the original binary with
  the same name (so `slay`, `pidin` and the starter still find it). In the car `/var` may not exist yet when the wrapper runs: it falls
  back to `/fs/sda1/opt/hmi/data/ID5`.
- Processes talk to each other through small files in `/dev/shmem` (see [Files on the head unit](#files-on-the-head-unit)).

## The menu plugin (`src/cpm.cpp`)

- **Plugin ABI** (mapped by NBT-AAD): `pluginAppInfo = { version 1, "CarPlay Advanced Settings", vendor "CarPlay Advanced", rhmi 1,
  create, destroy }`. `CarPlayMenu_create(IDispatcher&, name, params, config)` mallocs 0x200 bytes and placement-constructs
  `bmw::PluginApp` with the framework's constructor (`_ZN3bmw9PluginAppC1E...`, libAppFramework), then swaps in a copy of its vtable
  (`_ZTVN3bmw9PluginAppE`, 2 header words + 41 slots) with slot 22 (`onInit`) replaced. `appOnInit` registers the action handlers
  (`addHandler(actionId, {object, stub})`), calls the base `onInit`, and sets every model (`updateModel(modelId, bool)`).
- **Manifest and menu**: `CarPlayMenu.manifest` (`<file>{pluginDir}/CarPlayMenu</file>`, DescFile, TextDBFile). `CarPlayMenu.xml` uses
  `applicationType="Custom"` with `insertStateID="20"` (the Media/Radio list `ST_Ent_Selection`) and `insertAfterFocusID="8195"`
  (right after "Now playing in Apple CarPlay"; without that row it sits after AM). Options are checkboxes (`raAction` +
  `raBoolModel`), submenus are buttons with an `hmiAction` to their own `hmiState`, and the sensitivity levels are radio buttons (the
  plugin sets all three models), as are the HUD effect colours. Texts come from `src/texts.py`, English in every HMI language (100000 = the language name).

| Menu row (state) | Action / model | Switch file | Applies |
|---|---|---|---|
| Full-screen CarPlay (20) | 5 / 12 | `fullscreen` | after Restart to apply |
| CarPlay directions in HUD | 8 / 19 | `hud_guidance` | drawing at once; the iPhone's guidance from mm-ipod's next start |
| HUD effects > (81) Fill toward the turn | 84 / 85 | `hud_fill` | after restart (read when the HUD starts) |
| ... > Blink near the turn | 88 / 89 | `hud_blink` | after restart |
| ... > Effect colour > (93) Orange / Grey / White | 96-98 / 99-101 | `hud_colour` = 5 / 3 / 4 (no file: 5, Orange) | after restart |
| iDrive control > (41) Enable knob tilts | 6 / 17 | `remap_knob` | after restart |
| ... > Touchpad > (44) Enable touchpad | 7 / 18 | `remap_touchpad` | after restart |
| ... > Touchpad > Tap touchpad as click | 46 / 47 | `tap_click` | at once (hook installed) |
| ... > Touchpad > Touchpad sensitivity > (50) Low / Medium / High | 52-54 / 55-57 | `touchpad_mm` = 100 / 175 / 250 (no file: 250, High) | after restart |

  How to add or change rows: the `hmi-menu` skill (`check_menu.py` checks that the XML, `texts.py` and `cpm.cpp` agree).

- Most switches apply at start (`applyAtStart`, when the HMI loads the plugin): HMI patches, hooks, wrappers and links. A menu change
  writes the file, makes or removes links, and logs `(applies after restart)` when it does not apply at once.
- `menu_v2`: on its first start the current plugin converts the older flat menu's switches (a touchpad option on -> "Enable
  touchpad" and "Tap touchpad as click" on).
- Build detection (`detectBuild`): the build name in `/opt/hmi/ID5/data/ro/version.txt` picks a `kBuilds` entry. No match = **menu
  only**: nothing is written into the HMI. Log: `/dev/shmem/carplaymenu.log`.

## HMI code patches and hooks

- **Writing code** (`patchWords`): HmiMain3D's text cannot be made writable, so each page is replaced by a private anonymous copy
  (`mmap` RWX, copy, write the words into the copy, then map it over the original). Every word is compared with its expected
  original first (a word that already has the new value counts as done); **nothing is written if any differs**.
- **`kBuilds`**: per build `touchFn`, `ctlSetFn`, `ctlProxy`, `playFn`, `playObj`, the `CTouchData` offsets, tilt words, fullscreen
  words, layout variant and ini flag.

| Build | `handleTouchInput` | controller send | track send | `CTouchData` list / time / origin |
|---|---|---|---|---|
| `ID5_1803-510-1749MA Build 71` (006_017_006) | 0x43c02c | 0x1fd0d8c | 0x1fd0cec | +4..+8 / +0x14 / +0x18 |
| `ID5_1703-490-1650ZD Build 139` (006_006_006, NBTevo_M17345I, MINI F54) | 0x8f55cc | 0x20d9e50 | 0x20d9db0 | +8..+0xc / +0x18 / +0x1c |

  1703 was mapped from 006 by matching functions instruction by instruction: `handleTouchInput` and `handleControllerInput` are the
  same code, and its `CTouchData` has a reference count at +4. The proxy offsets are the same (`*(activity + 0xb0) + 0x4e60` for the
  controller, `+ 0x52b0` for playback).
- **Knob tilts** (`carplay_tilt`; `src/tilt_*.json`, generated into `out/tilt.inc`): `CCarPlayActivity::handleControllerInput` sends
  the controller to CarPlay as `CAuxIn_CarPlayControllerInput` (proxy, rotation, press, back, up, down, left, right, voice). Stock, the
  four direction fields are hard-coded 0: tilt up/down are dropped, tilt left goes out as Back, and tilt right moves the HMI's side
  panel. The patch widens the key filter to 9..14 (tilt up 9, down 10, left 11, right 12, rotate 13/14), stops tilt left setting Back,
  and reuses the 16 instructions of the function's trace printf to zero the four direction words and set "pressed" in the one for
  key - 9 before jumping to the send call. On 1703 the words are the same except two branches whose distance changed.
- **Controller send hook** (`installCtlHook`): even with the directions filled in, Connectivity turns the HMI's message into a
  `KnobEvent` without directions, so the send function itself is hooked. It is an entry hook: the first two instructions (`push
  {r4-r8,fp,lr}; add fp,sp,#0x18`, checked) are replaced by `ldr pc,[pc,#-4]` + our address, and a trampoline page (mmap RWX) holds
  the two original instructions and a jump back. `controllerHook` writes every direction to `/dev/shmem/carplaymenu-knob` (for
  `libcppinch.so`) and calls the original with the directions cleared (otherwise they came out as "select"). A call without a
  direction after one is its release: it is written with a flag, keeping the direction in case the press was overwritten.
- **Touchpad hook** (`installTouchHook`, the same entry-hook technique on `handleTouchInput`; it also checks the controller and track
  send entries): the HMI sends the controller's touchpad (origin 2/3) to CarPlay as `CarPlayTouchPadInput`. With "Enable touchpad"
  the hook decides per gesture (from the first finger down to the last one up):
  - one finger goes on to CarPlay's touchpad;
  - "Tap touchpad as click": a tap (< 350 ms, < 24 units of movement) = knob press (CarPlay's touchpad has no select);
  - "Two fingers tap to back": two-finger slides (their centre, 64 units a step, while sliding) = tilts, a short two-finger tap = Back. Two fingers
    are a slide only if the centre moves more than their distance changes; otherwise it is a pinch, passed on.
  - Every event writes both fingers to `/dev/shmem/carplaymenu-pad` (for `libcppinch.so`).
  - The finger record is `u16 x, y, z, u8 type, state (1 down, 2 move, 3 up), id`. **In the car the second finger comes without a
    position** (x = y = z = 0xffff, the same id 0). It counts as finger 2 resting on finger 1, so slides work but pinches cannot be
    measured.
  - Screen touches (origin 1), and the touchpad without "Enable touchpad", go to the original code unchanged.
- Test switches of the hooks:
  - `touchpad_tilts`: one finger = tilts every 64 units (the pre-2026-11-12 behaviour).
  - `media_gestures` (with "Enable touchpad", without "Two fingers tap to back"): two fingers up/down = volume +1/-1 every 40 units, sent as MOST
    `AudioMaster` 0x20/00 `VolumeActual` 0x200 Increment/Decrement through `hud.h`'s client; right/left once per gesture = next/previous
    track through `CAuxIn_iAP2PlaybackControl`.
  - `touch_log`: the first 120 touchpad events, raw. `ctl_log`: every controller send call.

## Full-screen CarPlay

Three parts, all needed:

1. **The layout slot.** The MINI brand layout `mini/id5/widget/generated/Spec_State_Merged.pbw` (protobuf) gives CarPlay a 750 px slot
   next to the side panel. `pbwpatch.h` rewrites the original into `carplaymenu/Spec_State_Merged.pbw` with a 1180 px slot at x 49,
   and it is linked with `ln -sP` over **both** paths the HMI may use (`/opt/hmi/data/ro/...` and `/opt/hmi/ID5/data/ro/...`). Both
   links are removed before the original is read: with only one, the plugin read its own copy, did not recognise it and deleted it, so
   full screen came and went on alternate starts. The HMI reads layouts when it starts, so the first start after an update still shows
   the side panel. 006 (`pbw::patch`) keys on `IsCarPlayFullscreen`; 1703 (`pbw::patchFixed`) names things by string and sets the
   `LT_State_CarPlay` slot directly. On a BMW the layout is another file (below).
2. **The side panel flag (006 only).** With the `CARPLAY_FULLSCREEN` coding, variant 0x9C71 is kept at `CCarPlayActivity + 0x108` and
   hides the side panel. The constructors run before the plugin loads, so the plugin forces the six `ldrb [rN, #0x108]` reads and the
   variant query at 0x43c0c0 to 1 (`kFsCode`). 1703 has no such flag (its getters return constants), so the layout alone does it.
3. **The size the iPhone renders** (`iniwide.h`): the MINI `[Screen]` sections (750_480; 711_480 with display resolution 1) become
   **1184** wide, with `PhysicalWidth=194` (the stock 6.1 px/mm) and the picture drawn 1180 wide (`dstw=1180` in the VideoURL). **The
   iPhone declines 1180 x 480** (it joins the car's Wi-Fi and never offers CarPlay) but takes 1024, 1152 and 1184 (multiples of 16);
   1184 -> 1180 is invisible. A smaller size does not scale up: 1024 x 416 showed CarPlay cut off (car, 2026-11-13); 1200 x 480 and
   1472 x 600 connect and fill the slot whole. The change goes to Connectivity's working copy (`ini::patchConn` -> `carplaymenu/carplay-conn.ini`,
   linked over `/var/opt/conn/carplay/carplay.ini`) and to the template copy (`ini::patch` -> `carplaymenu/carplay.ini`), for when
   Connectivity rewrites the working copy. Test switch `fullscreen_ini`: the ini on builds whose `kBuilds` entry has `ini 0`.
   The plugin writes the working copy when the HMI starts, before the iPhone's first connection, so a `[Screen]` written by hand
   before a reboot never reaches the iPhone. For size tries use the test switch `screen_size` "<width> <height> <mm wide> <mm high>"
   (with Full-screen): it replaces `Width`, `Height`, `PhysicalWidth`, `PhysicalHeight` (`patchConn`'s `scr`), and the log line
   says so. 1472 x 600 at 194 x 78 mm reached the iPhone: the same layout, no Dashboard.

**BMW** (and BMW i, Rolls-Royce; from the 2018 PSdZData, not tried in a car):
- **Which layout.** The brand packages are split by the head unit's part: MINI parts carry `swfl_2716` (`mini/`) and `2717` (`bmwi/`,
  id6l only), the larger BMW parts `2718` (`rr/`) and `2719` (`bmw/`). `bmw/id5` has no `Spec_State_Merged.pbw` and `rr/id5` has one
  without `LT_State_CarPlay`, so those cars use the state in the HMI package's own
  `/opt/hmi/ID5/data/ro/common/widget/generated/Spec_State_Merged.pbw` (223 KB on 006, 429 KB on 1703); MINI's `mini/id5` state
  overrides it. The plugin decides by the car's brand (`brandMini`): `HMI_BRAND` from its environment (the launcher's StarterPlugin
  exports the coded brand, `ENV: HMI_BRAND=02` in the MINI's sloginfo; 02 = MINI, 00 BMW, 01 BMW i, 03 Rolls-Royce by the coding's
  `va_HMI_BRAND_*` order), else MINI if the MINI layout exists (a smaller-screen BMW may carry the MINI package too). The choice is logged.
- **The common layout** is designed for 1440 x 540 (constregistry: `screenW` 1440, `smallScreenW` 900, `contentPreviewW` 540; the 10.25"

## Knob, touchpad and zoom (`src/pinch.c`)

`libcppinch.so` runs in Connectivity whenever a controller or touchpad option is on. It interposes functions that `libconn_carplay.so`
and `libconn_carplaydevctrl.so` call through their PLT/GOT (`R_ARM_JUMP_SLOT` / `R_ARM_GLOB_DAT`); the original is reached with `dlsym`
on the next library. Log: `/dev/shmem/cppinch.log` (with `debug_log`: the first calls of each kind, then every 256th).

- **Knob directions.** `CCarplayServiceMgr::setKnobEvt(select, home, back, x, y, wheel)` is how the controller reaches the iPhone's
  knob HID. The object comes from the interposed `CCarplayServiceMgr::start(config)` (and every `setKnobEvt`). A thread reads
  `/dev/shmem/carplaymenu-knob` and sends `setKnobEvt(0,0,0,x,y,0)` and a release. Two findings from the car:
  - `setKnobEvt` zeroes x/y unless `[KnobInput] NudgeSupport=YES` is in the ini `start()` parsed (Connectivity's working copy, at its
    start). `iniwide.h` adds it; the knob descriptor then grows from 0x23 to 0x36 bytes and the report from 2 to 4.
  - X/Y are absolute axes -127..127 (`09 30 09 31 15 81 25 7f 75 08 95 02 81 02`), so +-1 reads as centred. A nudge is sent at
    **+-127 for 80 ms** (test switch `knob_nudge` "<size> <ms>").

  One nudge = one list item, or one map jump in Apple Maps. A held tilt repeats: the first after 500 ms, then every 350 ms until the
  release (`no_knob_repeat` turns it off). The HMI reports the release up to ~150 ms after the hand lets go (car, 2026-11-13: an
  extra item after some holds), so each repeat is held back 200 ms past its due time and dropped if the release comes first
  (`REPEAT_FIRST` 300 + `REPEAT_HOLD` 200 keeps the first at 500 ms; the due times keep their 350 ms rhythm, `next += every`).
  `knob_repeat` "<first> <every> <hold>" changes the three.
- **Touchpad.** CarPlay gets a touchpad only through the working copy: `[TouchPadInput]` 0..511 (the HMI's units), `PrimaryInput=YES`
  (with the knob primary the iPhone ignored it), and the physical size from "Touchpad sensitivity" (the iPhone scales a slide by it:
  50 and 100 mm were slow, 250 good). The stock touchpad HID has one contact plus two handwriting channels. `getHIDDescriptor_TouchPad`
  is replaced with a two-finger descriptor (each finger collection gets a Transducer Index, 0x38) and `touchPadUpdate` with a 26-byte
  report; finger 2 comes from `/dev/shmem/carplaymenu-pad`, scaled by finger 1's ratio. In the car the iPhone ignores a second
  touchpad contact (and the controller gives none), so **pinch on the touchpad does not work**. Test switch `no_pinch`: the one-finger
  HID only.
- **Rotation as map zoom** (`knob_zoom`; in the car 2026-11-13: Apple Maps zooms, Google Maps does not). The knob HID has no zoom
  usage and the library declares no zoom key, but Apple Maps pinches on a two-contact touchscreen.
  - `readConfig` reads a `[TouchScreen]` section; the plugin adds one without `PrimaryInput`, so the knob and touchpad stay primary.
  - `getHIDDescriptor_Touch` (a 62-byte template, one finger) is replaced with a two-finger one (129 bytes, as LIVI's), and
    `touchUpdate` with a 12-byte report.
  - A rotation (`setKnobEvt` with only a wheel value) is answered with one pinch through `setTouchEvt`: both fingers on a horizontal
    line **in the top bar** (centre at 10/16 of the width, 1/16 of the height; `ZOOM_X16` / `ZOOM_Y16`), the half-distance starting
    at h/8 and growing x1.5 a step (at most 4 steps), 9 reports 16 ms apart plus 3 still ones, then both lifted. Positive wheel =
    zoom in; `zoom_reverse` swaps the directions. Through the middle of the screen a pinch outside a map was a tap on the list row
    under it; in the top bar it taps nothing and Apple Maps still zooms. Google Maps does not zoom (60 px down already taps list
    rows). Test switch `zoom_at` "<x/16> <y/16> <dir 0 horizontal, 1 vertical, 2 diagonal> <start half distance px>" moves it
    (`zoom_place`); the fingers are kept on the screen.
  - Rotation then no longer moves the CarPlay focus.

## Route guidance from the iPhone (`src/rghook.c`)

The 2017 iAP2 stack (mm-ipod, "Media 1.0.70") predates CarPlay route guidance. `librghook.so` is preloaded into mm-ipod and touches
only `read()` / `write()` on the iAP2 transport descriptor (found by its first iAP2 bytes `ff 5a` / `ff 55`, or `$RGHOOK_DEV`). It is
first in `LD_PRELOAD`; other `write()` calls go to the next library in the chain (QNX has no useful `RTLD_NEXT`, so it walks
`LD_PRELOAD` itself). `close()` is not hooked: mm-ipod calls it while libraries are still loading, before libc can be looked up.

- **Outgoing**: `IdentificationInformation` (0x1D01) gets 0x5200/0x5203 added to MessagesSentByAccessory, 0x5201/0x5202/0x5204 to
  MessagesReceivedFromDevice, and a `RouteGuidanceDisplayComponent` (param 30: id 0x0F0E, name "Head-Up Display", 256-character
  limits, 6 maneuvers, lane guidance); lengths and checksums are fixed.
- **Inject**: `StartRouteGuidanceUpdates` (0x5200) goes out once **both** `IdentificationAccepted` (0x1D02) and
  `AuthenticationSucceeded` (0xAA05) have arrived: a real iPhone identifies first and authenticates afterwards, and ignored a request
  sent between the two. The packet takes the next link sequence number; every later driver packet is renumbered (+delta) and every
  acknowledgement the phone sends is shifted back (-delta), so both ends see a gap-free link.
- **Incoming**: route-guidance packets are decoded and handed to the driver as a minimal message it knows (an empty `PowerUpdate`
  0xAE01 with the same sequence number; `$RGHOOK_SUBST` changes it). **The 2017 driver leaks the receive buffer of every message it
  does not know**, and after about 20 route-guidance messages it stopped reading the link. Only a packet header split across reads is
  held back (at most 8 bytes).
- **Decode** (layout as the community MIB2 implementation, `rgd_tlv.h`):
  - `RouteGuidanceUpdate` 0x5201: route state, maneuver state, current road, destination, distance + string + units, remaining
    distance, current maneuver index (13), lane index (16) and lanes showing (18), source.
  - `RouteGuidanceManeuverUpdate` 0x5202: index, description, type 0..53, road, step length, exit angle, driving side, junction type
    and angles; 32 kept by index.
  - `LaneGuidanceInformation` 0x5204: index and lanes (position, status 0 not good / 1 good / 2 preferred, angles, highlight angle
    with 1000 = none); 8 sets of up to 8 lanes, sorted left to right.
- **Output**: `/var/iap/pps/routeguidance`, PPS-style `key::value` lines, written to `.tmp` and renamed: route_state,
  dist_to_maneuver(_string, _units), current_road, maneuver_index/type/exit_angle/driving_side/road/junction_*, and lanes
  (`status/highlight/angle,angle;...`, while the iPhone shows them). Every message also goes to `/var/iap/rghook.log` with `debug_log` (without it: `RG route_state <n>` when it changes). The file is
  removed when mm-ipod starts, so a new session never shows an old route.
- **For the senders in mm-ipod** (`rgview.h`):
  - The decoded state is updated under a sleep-based lock (`st_lock`): mm-ipod's threads have different fixed priorities, and a spin
    on `sched_yield` once starved the holder.
  - `rg_view_get()` copies the same fields `hud.h` reads from the file.
  - After every message, `kick()` calls `rgk_kick()` / `rgh_kick()` in the KOMBI / MOST builds; the plain build calls nothing.
  - The file helpers use rghook's own libc pointers, because its `read` / `write` are the hooks.

## Directions on a MOST HUDTerminal (`src/hud.h`, `src/hudshapes.h`)

The BMW navigation draws its maneuvers itself on the cluster's `HUDTerminal` (MOST FBlock 0x82, instance 0): polygons, texts and
double buffers. The HUD shows what the cluster's guidance shows. `hud.h` does the same with the iPhone's guidance; it runs in the HMI
(menu plugin) or in mm-ipod (`librghook-most`, `-both`).

- **MOST client**: `libsys_dsi_colibry.gpp.so.8` is loaded with `dlopen` and its DSI classes are called by mangled name
  (`CDSIConnection`, `CDSIClient("DSYSMOSTServer", "MOSTSubSystem", 4, 5)`, `CDSIOStream`). The client's vtable is copied with slots
  3/4/7 (attached, detached, data) replaced. Layout checked on 006: channel at +0x130, socket +0x138, fd +0x140; in the stream, id
  +0x48, data +0x10, size +0x08. The client registers as `CarPlayHud`, subscribes to the registry, messages and client responses, and
  learns its own device address and the host of 82/00 from the registry. Each call is a `StartResultAck` method (op 6) to that host;
  the cluster answers `ResultAck` (op 0xD) or `ErrorAck` (op 0xF).
- **Calls**: `SetVisibility` 0x204, `SwitchVisibility` 0x20E, `SetText` 0x210 (UTF-16BE), `SetLineWidth` 0x219, `SetFillColor` 0x21B,
  `AddPolygon` 0x21D (filled polygon, type 3; the cluster takes up to 99 points), `RemoveAll` 0x220. Handles (6WA profile, F20, from NBT-AAD):
  1 the panel, 2 street, 3 distance, 4 unit, 5 and 6 the double-buffered picture. Fill colour 4 = the route (white, the factory
  colour), 3 = the context tone (grey; it was 0x0A until 2026-11-13, which is transparent on the F54: two-colour pictures lost their
  second colour).
- **Loop** (`worker`, every 0.5 s, every 1 s without a route): read the routeguidance file.
  - A new maneuver (type, index, angle, junction, lanes, road) draws the picture into the hidden buffer and swaps it in
    (`SwitchVisibility`), then sets the three texts and the panel.
  - A new distance updates only the texts (and the HUD effects' level, below).
  - Route state 3/4 (Loading / Locating) keeps the last picture.
  - No active route clears to the state the BMW navigation leaves at the end of a route.
- **The BMW navigation wins**: any other client's drawing call on 82/00 (not an echo of ours; recent calls are hashed) means the BMW
  navigation is guiding. Nothing is drawn until 5 s after its last call, then the picture is drawn again.
- **Picture box**: the shapes are drawn in the 6WA box (70,20)-(170,120). On a MINI (its layout present) every point is mapped to
  (35,15)-(85,65), where the F54 cluster's own navigation draws (captured in the car). `hud_box_6wa` keeps the 6WA box; `hud_mono`
  draws everything in the route colour.
- **Pictures** (`hudshapes.h`): Mapbox's maneuver drawings (`hudglyphs.h`, generated by `tools/hud_glyphs.py` from
  mapbox-navigation-ios v0.40.0 `ManeuversStyleKit.swift`), turned into filled convex pieces, for all 54 iAP2 maneuver types.
  Regenerating, previewing and changing them: the `hud-glyphs` skill. The pieces of one tone that share an edge are joined back into
  whole polygons (`mergePieces`, up to 96 points): a few MOST calls a picture instead of up to 96. Always on since 2026-11-13 (the
  F54 fills non-convex polygons cleanly and the pictures look the same); the test switch `hud_convex` draws the pieces.
  - The roundabout is Mapbox's parametric drawing for any exit, with thin roads for the exits passed (2..4), or the junction's roads
    when the iPhone sends them; the exit number is shown from exit 5.
  - There is also a ferry picture. Left-hand traffic is mirrored (digits never).
  - Lanes: a strip under the picture (which is made smaller, 10/16), y 84..119 of the box (17 px on the MINI), lanes up to 26 units
    wide. Each lane is one of Mapbox's lane drawings (`LanesStyleKit.swift`: straight, slight, turn, U-turn, straight + turn with the
    way not to take grey), mirrored for the left; lanes to take in the route tone, the others grey. One scale for the strip: full height
    unless the widest drawing would not fit its lane. Lanes verified in the car (2026-11-13) with the first, hand-made arrows (bands and
    triangles), which looked poor; the Mapbox ones are not in the car yet. `.claude/skills/hud-glyphs/preview.py ... --lanes ... --mini`
    shows them as the MINI draws them. A picture may have up to 192 pieces (kMaxPieces); whole polygons join them for the MOST calls.
  - No floating point; angles use a sine table.
- **HUD effects** (menu "HUD effects"; switch files read when the HUD starts, so they apply after a restart). They touch only the
  maneuver, never the lanes, and never the start marker (type 11). Range (mib2q-carplay-rgi's bargraph rule): the iPhone's step length (`maneuver_step_length`), at most
  300 m (`hud_fill` may hold "<cap metres> <colour>").
  - **Fill toward the turn** (`hud_fill`): from the step's start the maneuver fills with the effect colour from the bottom up, in 8
    levels, full at the turn (`applyFill` cuts pieces at the level line).
  - **Blink near the turn** (`hud_blink`): in the last fifth of the range the maneuver blinks, 600 ms a phase, route colour <->
    effect colour. Both phases sit in the two picture buffers and `SwitchVisibility` swaps them: one MOST call a phase. The loop
    runs every 300 ms while an effect is on.
  - **Effect colour** (`hud_colour`, radio buttons): Orange 5 (default), Grey 3, White 4 (the route's own colour).
  - Checked in the car with a pretend route (`tools/hud_sim.sh`): levels and blink as designed. Day colours and a real drive are open.
- **The F54 HUD terminal** (measured in the car, 2026-11-13, with `tools/hud_probe.sh`):
  - `ImageGetSize` (C04) takes the handle only, `[inst u16]` -> `op d [inst][w u16][h u16]`; the 6WB form with a 01 byte is refused
    (`op 9` ErrorAck, code 05 invalid length).
  - Surfaces 0x01-0x17: 0x01/0x10 408 x 116, 0x02 250 x 27, 0x03/0x11 69 x 24, 0x04 33 x 21, 0x05-0x08/0x0e/0x0f 120 x 72,
    0x09/0x0a 184 x 17, 0x0b 227 x 72, 0x0c 62 x 22, 0x0d 33 x 22, 0x12 32 x 21, 0x13/0x14 250 x 116, 0x15/0x16 172 x 116,
    0x17 39 x 39; 0x18 and up 0 x 0.
  - No distance bar: `PotentiometerSetValue` (227) sweeps on 0x09, 0x0a, 0x02, 0x15, 0x16 are accepted but show nothing, and the
    BMW navigation draws no bar on this HUD either.
  - Non-convex polygons (`AddPolygon` 21d) fill cleanly (notched arrow, 22-point half ring, swallow-tail flag).
  - Fill colours (`SetFillColor` 21b) at night: 0 4 6 7 white, 2 5 11..31 orange, 3 8 grey, 1 9 10 transparent (10, the context
    tone, only cuts the white away). The BMW navigation uses 4 and 5. Day colours not checked.
- **Test channel**: `/dev/shmem/carplaymenu-hudcmd`, one call per line `"<fkt hex> <payload hex>"`, run once, to try a cluster's
  layout without a rebuild. The first 600 HUDTerminal messages in both directions go to the log, and each batch restarts that count
  so its calls and the cluster's answers are logged. `tools/hud_probe.sh` (run on the head unit, with "CarPlay directions in HUD" on
  and no route) drives it: `sizes` (F54 form; `sizes6wb`), `bar`, `concave`, `colours`, `vis`, `raw`, `seen`, `log`.
  `tools/hud_sim.sh` writes a pretend route into `/var/iap/pps/routeguidance` with a counting-down distance.

## Directions on an Ethernet KOMBI (`src/kombi.h`, `src/rgkombi.cpp`)

G-series and J29 clusters (Ethernet KOMBI) have no `HUDTerminal` on MOST. Their KOMBI has its own route-guidance service,
**BMW.IC.Guidance, SOME/IP service 0xB006, TCP `160.48.199.96:30502`**, which draws the arrow, distance, street and lane row in the
cluster and the HUD. `kombi.h` ports NBT-AAD's car-verified stack (J29; ftojke's G30 CarPlay HUD uses the same one) to freestanding
C++. **For the same inputs it produces NBT-AAD's bytes** (checked when it was ported; the street is cut to 40 characters, as their
display layer does).

- **Graph** (`Graph`): every frame is a byte copy of NBT-AAD's captured factory route start (`kombitemplate.h`, 97 frames, instance
  handle 0xC8) with only proven fields changed:
  - `ManeuverDescription` 0x0F: the direction at body[33].
  - `ManeuverDistance` 0x1D: UTF-16BE text at the FEFF BOM, then the unit byte (0 km, 1 mi, 3 m, 4 yd, 5 ft); the red bar at body[22]
    (255 = hidden).
  - `TextResource` 0x03: the street.

  Body layout: `[0:4]` handle, `[4:8]` model id, `[8]` type, `[9:13]` length - 17, `[13:17]` tag.
  - `start` sends the whole graph; `maneuver` the factory's in-place update block (text resource .. guidance state 2, 9-10 frames);
    `distance` one frame; `cancel` the factory's 6-frame cancel (state 7 -> 5 -> 0, empty list, init, destination clear), and
    `cancel(state0Only)` only its state-0 frame.
  - Lanes: one lane model 0x1B (method 0x0010) before each of maneuver 0's two 0x0F nodes, which then list it; the template's own lane
    models are dropped (93 frames). A lane is `{1, kind (1 take, 2 other), 1, 1 arrow, 0, 0}`, followed by boundary bytes, then the
    section (route positions d0 = d1, length d2). The KOMBI shows the row while the car's route position from the last 0x11
    destination info lies inside the section, re-checked on every 0x11; `position()` sends one, at most once a second, when it moved.
  - Doubles of whole metres are built and read by hand (`uToF64`, `f64ToU`): the car's libc has no soft-float.
- **Client**:
  - SOME/IP request header `B0 06 <method> <len = 8 + body> 7E 01 <session> 01 01 00 00` (our client id 0x7E01, interface 1,
    REQUEST). A reply must be the matching E_OK (`80 00`) for the same method and session.
  - KOMBI magic cookies (`FF FF 80 00`) are skipped (up to 4 per reply) and drained before each request.
  - **Only whitelisted methods** (2, 3, 4, 9, 0xA, 0xB, 0xC, 0xE, 0x10); never 1 (create / dispose), because the factory owns the
    instance.
  - One persistent connection. A connection error gets one reconnect and that frame again (updates are idempotent); a non-E_OK reply
    is "rejected". The cancel runs on fresh connections (sessions 400.., then the state-0 frame at 500).
- **Sockets without libsocket at link time**: `socket`, `connect`, `send`, `recv`, `setsockopt`, `getsockopt` and `getpeername` come
  from `dlopen("libsocket.so.3")` (then `.2`, then `.so`). Connect with a timeout is a non-blocking `connect`, then `getpeername` every
  20 ms until it succeeds or `SO_ERROR` is set (no `poll`: its flags differ). QNX io-pkt constants, checked against ftojke's QNX build:
  `O_NONBLOCK` 0x80, `F_GETFL`/`F_SETFL` 3/4, `SOL_SOCKET` 0xffff, `SO_SNDTIMEO`/`SO_RCVTIMEO`/`SO_ERROR` 0x1005/0x1006/0x1007,
  `IPPROTO_TCP` 6, `TCP_NODELAY` 1, `MSG_PEEK` 2, `MSG_DONTWAIT` 0x80, BSD `sockaddr_in` with `sin_len`, 8-byte `timeval`.
- **Display** (`Output::tick`, from NBT-AAD's `j29_display.cpp`):
  - A new maneuver or street sends an in-place update if one is shown and in-place works, else the whole graph.
  - A rejected in-place update means whole graphs from then on. A rejected whole graph or distance turns the output off until the
    process restarts. A link error retries after 5 s with the whole graph.
  - A lane change on the same maneuver resends at most every 3 s.
  - No route sends the cancel.
- **iAP2 -> KOMBI** (`direction`, `laneArrow`, `manOf`):
  - Maneuvers: left/right 6/7, slight/keep 2/3, sharp 4/5, U-turn 8/9 by traffic side, roundabouts 14 (clockwise, left-hand traffic)
    / 15, off/on ramps 28/29 and 25/26 by the sign of the exit angle (else the traffic side), lane change 32/33, arrival 10,
    everything else straight 1.
  - Lanes: status good/preferred = a lane to take. The arrow comes from the highlighted angle (else the first one): <=20 straight,
    <=60 half, <=120 normal, <=170 tight, else U-turn. A lane without a direction, or more than 8 lanes, means no lane row.
  - Distance: the number and unit from the iPhone's text ("450 m"), else whole metres, "-" with nothing.
  - Car-verified by NBT-AAD: LEFT 6, RIGHT 7, DESTINATION 10, lane arrows 1/2/6/7. The rest follow the KOMBI enum names.
- **Worker in mm-ipod** (`rgkombi.cpp`): started by the first `rgk_kick()`. Every 500 ms, while `hud_guidance` exists, it snapshots
  the state (`rg_view_get`) into `Output::tick`. Loading / Locating keeps the arrow. If the output fails, it stops for the session.
- **The BMW navigation wins** (NBT-AAD's `FactoryRouteWatch`, J29 log lines):
  - `sloginfo -w` is started with QNX `spawn` (stdout = a non-blocking pipe, stdin and stderr closed; tried at `/usr/bin`, `/bin`,
    `/proc/boot`), and its lines are read every tick.
  - "RouteGuidanceStarted" = a BMW route; "NaviRouteVisibleInMap sourceHandle = N" names it; "disable route: routeId N" for that route
    ends it. A disable of the old preview route ~1 s after a start does not end it. The log's first 3 s are its backlog dump.
  - While a BMW route runs, nothing is sent and our state is forgotten **without a cancel** (the factory graph replaces ours). When it
    ends, a whole graph is sent. A CarPlay route started during a BMW route releases the yield.
  - If `sloginfo` ends, it is restarted after 10 s; if it is missing, that is logged once and retried every 60 s.

## librghook variants, the cluster choice and left-over arrows

- Four builds; one of them is installed as `librghook.so` (same soname: the mm-ipod wrapper preloads that name).

| Build | `rghook.c` defines | + | Does |
|---|---|---|---|
| `librghook.so` | - | - | guidance file only; no network code |
| `librghook-kombi.so` | `RGHOOK_KOMBI` | `rgkombi.cpp` | + KOMBI sender |
| `librghook-most.so` | `RGHOOK_MOST` | `rghud.cpp` (`hud.h`) | + MOST drawing in mm-ipod |
| `librghook-both.so` | both | both | + both |

- **Cluster choice** (`carplaymenu/cluster`, written by the installer; **chosen at install time, nothing probes at run time**):

| Choice | Full install (menu plugin) | HUD-only install (no menu plugin) |
|---|---|---|
| `most` | `librghook.so`; the plugin draws on MOST | `librghook-most.so` |
| `kombi` | `librghook-kombi.so`; the plugin draws nothing (`hud.h kombiOnly`) | `librghook-kombi.so` |
| `both` | `librghook-kombi.so`; the plugin draws on MOST too | `librghook-both.so` |

  The default comes from the installer's probe (`libcpprobe.so`: a TCP connect to 160.48.199.96:30502, closed at once, nothing
  sent): KOMBI found = `kombi`, else `most` (also when the probe gives no answer). The probe cannot see a MOST HUDTerminal, so `both`
  is only available with `--cluster both`. There is one MOST sender either way (the plugin or `librghook-most/-both`, never both).
- **Left-over arrows**: mm-ipod lives for one CarPlay session, and a session ending with an arrow up would leave it on the cluster.
  - While an arrow is shown, `RG_KOMBI_MARKER` (`/dev/shmem/carplaymenu-kombi.shown`) or `RG_MOST_MARKER`
    (`/dev/shmem/carplaymenu-most.shown`) holds mm-ipod's pid.
  - Once per mm-ipod, `rg_watch_once()` (rghook.c) spawns a watcher with `spawnle(P_NOWAITO)`, so it outlives mm-ipod (its environment
    is minimal, without `LD_PRELOAD`): `while kill -0 <pid>; do sleep 3; done`, then `CPM_CLEAR=<pid> LD_PRELOAD=libcpprobe.so
    /bin/cat`.
  - The probe clears each marker that **still names that pid**; a newer session's arrow is left alone. For the KOMBI it sends the
    cancel; for MOST it uses its own `hud.h` client (`dsiOpen`, wait up to 8 s for registration and the 82/00 host, `drawClear`).
  - A new KOMBI worker also clears any marker it finds before it draws.

## Boot, restart and the bootloop guard

- **Boot hook**: one line after the shebang of `/bin/start_screen.sh` runs `boot.sh` from
  `/fs/sda1/opt/hmi/data/ID5/Plugins/CarPlayMenu` (falling back to `/var/...`). The HMI waits for `/dev/screen`, which that script
  creates, so the line always runs first. This is the only change to the system partition. The installer compares the line only up to
  its `#`.
- **`boot.sh`** reads the switches from `/var/opt/hmi/data/rw/carplaymenu` or, at boot, `/fs/sda1/opt/hmi/data/ID5/carplaymenu`, and
  makes the path-manager links: the layout over both paths (`fullscreen`; MINI's, or on a BMW `Spec_State_Merged-common.pbw` over the
  common layout's two paths, whichever the plugin wrote), the template and working `carplay.ini` copies when the
  plugin left them, the mm-ipod wrapper (`hud_guidance`) and the Connectivity wrapper. Only a link is ever replaced, never a real file.
- **Bootloop guard**:
  - `boot.sh` writes `boot_pending` at every boot. The plugin deletes it after the HMI has run **60 s** (`startStableTimer`), and
    Restart to apply deletes it before its reboot.
  - If it is still there at the next boot, that boot failed (an HMI crash and watchdog reset, or a power cut in the first minute).
    `boot_strikes` counts failed boots in a row.
  - **3 in a row -> safe mode** (`safe_mode`): `boot.sh` makes no links and the plugin applies nothing (no patches, hooks or
    wrappers; the menu only saves switches) until Restart to apply, which deletes `safe_mode`.
  - **3 more in safe mode -> the plugin is disabled** (its manifest renamed to `CarPlayMenu.manifest.disabled`).
  - One failed boot alone changes nothing. `boot.sh` run while HmiMain3D is up (the installer's relink) leaves the guard alone.
  - Test hooks: `CPM_DIR`, `CPM_PLUGIN_DIR`, `CPM_LOG`.
- **Restart to apply**: `restart.sh` runs in a process of its own (`spawnl P_NOWAITO`). With the launcher (`/dev/starter`) it reboots
  the unit with `libcpreboot.so` (`LD_PRELOAD=libcpreboot.so /bin/cat`: `fdatasync` the switch files, `sync`, `sysmgr_reboot()`).
  Without the launcher it stops the HMI with the flag `/dev/shmem/carplaymenu-restart`.

## Installer (`carplay-advanced.sh`)

- POSIX `sh` on the computer (macOS, Linux) and QNX `sh`/`ksh` on the head unit: no bashisms, and none of the missing tools.
- **From a computer**:
  1. Checks `plugin/`: ELF headers via `dd` + `diff`, the ZIP signature, the manifest and XML, `ksh -n` of the scripts.
  2. Probes the head unit's port 22 with `nc` (macOS `-G`, else `-w`): no answer stops with what to check (a 169.254.x.x address on
     this computer, the ignition, the cable). Then one SSH master connection (`-M -S`, `LogLevel=ERROR`: OpenSSH's post-quantum
     warning about the unit's OpenSSH 5.2 is hidden); `uname -n` decides whether commands need `on -f hu-omap`.
  3. Reads `HmiMain3D` (`/opt/hmi/bin/zipped/HmiMain3D`, LZO-packed, read through ziploader as the plain ELF; else
     `/opt/hmi/bin/HmiMain3D`) and `libconn_carplay.so` over SSH and hashes them on the computer (the unit has no hash tool).
  4. Detects the generation (`KIND`): iDrive 6's `handleControllerInput` has, for keys 9..12, `isVariantSet(0x9c71); cmp r0,#0;
     movne <dir>,#1`.
  5. Uploads itself and the files to `/fs/sda1/opt/carplay-advanced-upload` with `cat`, reading each back and comparing.
  6. On a terminal, shows what it will install and asks "Proceed?" (`--yes` skips; a dry run or no terminal does not ask).
  7. Runs itself there with `--payload --kind --mode --hmi [--cluster]`, removes the upload, and copies the run's backup and the kept
     system originals to `BACKUP/` (with the head unit's full output as `installer-output.log`).
  8. Ends with a summary (what is installed or removed, where the backup is) and offers the restart.
- Output: a heading per step, ✓ / ! marks, the head unit's lines indented (colours only on a terminal, `NO_COLOR` turns them off).
- A restart never answers (the unit goes down with the connection open): `remote_reboot` runs it in the background, shows its lines,
  and stops waiting once the unit says it reboots ("rebooting the head unit" from libcpreboot.so, or OnOffDSICommander appreset).
- QNX `sh` with `set -e` exits when a loop body ends in a false `[ ] && ...` (the Mac's shells do not): write `if ...; then ...; fi`.
  /bin is `/fs/sda0/bin`, read-only until the installer remounts it. `/opt/hmi/data` is a link to `/opt/hmi/ID5/data`, and boot.sh
  links the layout under both spellings: removing a layout link removes both (`unshadow`; the MINI pair and the common pair). Both
  layouts' originals are kept (`Spec_State_Merged.pbw`, `Spec_State_Merged-common.pbw`); `status` shows both.
- **Modes**:
  - `full`: the whole plugin; the default on iDrive 5.
  - `hud` (HUD-only): no HMI patch, no reboot; the default on iDrive 6. There the HMI does fullscreen, tilts and the touchpad itself
    (variant 0x9c71), and a menu plugin is instantiated only with A4A / A4A_REMOTE_APPS / REMOTE_HMI / TOUCH_COMMAND coded
    (`CSpecialAppsHelper`). HUD-only builds the mm-ipod wrapper itself (a copy of the original mm-ipod + the librghook preload, with the
    `hud_guidance` switch), and installs the **HUD-only menu**: `cpm.cpp` built with `CPM_HUD_ONLY` (`libCarPlayMenu-hud.so`) and
    `CarPlayMenu-hud.xml` (build.sh cuts it from `CarPlayMenu.xml`: states 20 with the HUD row and HUD effects, 81, 93), staged as
    `libCarPlayMenu.so` / `CarPlayMenu.xml`, plus the marker `hud_only`. That menu patches nothing and hooks nothing; its toggles
    write the switch files (and link or unlink the mm-ipod wrapper for "CarPlay directions in HUD"), read by mm-ipod at the next
    CarPlay connection. `boot.sh` skips the bootloop guard when `hud_only` is there (an uncoded car never starts the menu, which would
    otherwise count every boot as failed and end in safe mode, taking the HUD down with it). `check_menu.py --hud` checks that XML.
    The entry point (state 20 after focus 8195 in Media/Radio) rendered on iDrive 6 in IDEmu (g30-bmw, A4A coded) with the full menu;
    the HUD-only menu itself is not tried on iDrive 6 yet.
- **On the head unit**: it refuses off hu-omap, without root (`pidin` effective UID), with an unsupported build, with two hook lines,
  or with a linked `start_screen.sh`. The plan is printed first; `--dry-run` stops there. Then a transaction:
  1. Backups to `/var/opt/carplay-advanced-backups/<time>-<action>`, with the system originals kept once in `originals/`; every copy
     is compared. Free space on `/var` is checked first.
  2. Staging: the payload, with the chosen librghook as `librghook.so`.
  3. Switch: from here on a failed step puts every moved directory back.
  4. After the commit, `boot.sh` relinks and `carplaymenu/cluster` is written. `--restart-hmi` reboots only after the backup copy.
- Actions: `install`, `uninstall [--keep-config]`, `status` (build, hashes, files, links, PIDs, the cluster probe and the recorded
  choice, backups), `restart`. Options: `--host`, `--dry-run`, `--restart-hmi`, `--yes`, `--full` / `--hud`, `--cluster most|kombi|both`.
- Known limitation: a second HUD-only install on top of one stops at "mm-ipod is missing or already a link".
- The tests redirect the path constants (one `NAME=` line each) and stub `uname`, `pidin`, `on`, `ssh`, `mount`, `df`, `sync`,
  `OnOffDSICommander`, `nc` and the probe host. A new path constant needs an entry in `tests/test_installer.py`.

  nothing is installed, and the installer prints a pre-filled GitHub issue link (`ISSUES_URL`). The plugin itself picks addresses by
  build name (`kBuilds`) and checks every word, so an unknown build gets the menu only.
- Adding a software: the hashes (from `status` on that unit, from the exact files of a car or package, never a modified copy), a
  `kBuilds` entry, the tilt words (`src/tilt_*.json`, mapped by matching functions with a known build), then its lines in
  `supported_table`. Between 006 and 1703, `libAppFramework`/`libCoreFramework` differ in 2-3 bytes, while `mm-ipod`,
  `libconn_carplay.so`, `libsys_dsi_colibry.gpp.so.8` and `carplay.ini` were identical.

## Status: verified and open

Verified in the car (MINI F54, HMI 1703, 2026-11-11/12): full width (iPhone 1184, drawn 1180, no side panel from the second start on),
all four tilts and held-tilt repeat, rotation and press, the touchpad as CarPlay's primary input (one-finger slides, tap = select),
two-finger slides and tap, HUD pictures and route guidance on MOST, the boot hook and links, and `libcpreboot.so`.

2026-11-13 (same HMI build):
- The submenus: every row shows its text, the checkboxes and radio buttons show and save their switches, each toggle is logged;
  "Restart to apply" reboots. The bootloop guard counted every boot as good.
- Rotation as zoom: Apple Maps zooms (pinch in the top bar); Google Maps does not.
- Held tilts: the HMI reports the release up to ~150 ms after the hand lets go (9 holds released 99-338 ms after the last repeat, an extra item after some); hence the 200 ms hold-back. Once, after a boot, tilts did nothing
  although every tilt reached `setKnobEvt`; a CarPlay reconnect fixed it (not pinned down).
- A lower render size (1024 x 416 into the same slot) shows CarPlay cut off; sizes at or above 1184 x 480 fill the slot.
- The voice button: a long press already opens Siri in CarPlay; nothing to change.
- HUD: whole polygons draw the pictures as before (no refused polygon); `hud_fill` / `hud_blink` behave as designed with a pretend
  route; the F54 terminal facts above (no distance bar, palette).

Open / not verified:
- 006_017_006 in a car (the working copy path, the touchpad, 1184).
- Any BMW in a car: full screen from the common layout (1440 x 540 / 1280 x 480), `HMI_BRAND` in the HMI's environment; the rest of the
  plugin (tilts, touchpad, HUD box) was only ever run on the MINI.
- Lag: 1152 x 480 / 1024 x 480 via `screen_size` are untried.
- HUD fill / blink in daylight (the palette may change with day / night) and on a real drive.
- The Mapbox lane drawings in the car (the lanes themselves were verified with the first, hand-made arrows).
- The Ethernet KOMBI output (tested only against a fake KOMBI), and NBT-AAD's log lines for the BMW-route yield on a G-series.
- `librghook-most` / `-both`: the MOST client inside mm-ipod, and the watcher's MOST clear.
- The bootloop guard in a car after a failed boot.
